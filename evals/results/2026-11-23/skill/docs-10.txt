# دليل المساهمة

شكرًا لاهتمامك بالمساهمة في المشروع! يشرح هذا الدليل خطوات فتح طلب الدمج (Pull Request)، وطريقة كتابة رسالة الالتزام (Commit Message)، والاختبارات التي نطلبها قبل قبول أي تغيير.

## قبل أن تبدأ

- ابحث في قائمة المشكلات (Issues) أولًا، فقد يكون غيرك قد أبلغ عن المشكلة نفسها أو بدأ العمل عليها.
- افتح مشكلة جديدة قبل أي تغيير كبير، واشرح فيها ما تنوي فعله، حتى نتفق على الطريقة قبل أن تبذل جهدك في كتابة الشيفرة.
- اقرأ مدونة السلوك (Code of Conduct) والتزم بها في كل تواصل داخل المشروع.

## تجهيز بيئة العمل

1. أنشئ نسخة مشتقة (Fork) من المستودع في حسابك.
2. انسخ نسختك المشتقة إلى جهازك:

   ```bash
   git clone https://github.com/<اسم-المستخدم>/<اسم-المشروع>.git
   cd <اسم-المشروع>
   ```

3. أضف المستودع الأصلي مصدرًا بعيدًا باسم `upstream`:

   ```bash
   git remote add upstream https://github.com/<المنظمة>/<اسم-المشروع>.git
   ```

4. ثبّت الاعتماديات وشغّل الاختبارات مرة واحدة للتأكد من أن البيئة سليمة قبل أي تعديل.

## فتح طلب الدمج

### أولًا: أنشئ فرعًا مستقلًا

لا تعمل على الفرع الرئيسي `main` مباشرة. حدّث نسختك أولًا، ثم أنشئ فرعًا (Branch) يصف التغيير:

```bash
git fetch upstream
git checkout -b fix/login-timeout upstream/main
```

نقترح أن يبدأ اسم الفرع بنوع التغيير: `feat/` للميزات الجديدة، و`fix/` لإصلاح الأخطاء، و`docs/` للتوثيق.

### ثانيًا: اجعل التغيير مركّزًا

- يعالج كل طلب دمج موضوعًا واحدًا. إذا أردت إصلاح خطأين غير مترابطين فافتح طلبين منفصلين.
- لا تخلط إعادة التنسيق أو إعادة الهيكلة (Refactoring) بإصلاح وظيفي في الطلب نفسه، لأن ذلك يصعّب المراجعة.
- حدّث التوثيق إذا غيّر تعديلك سلوكًا يراه المستخدم.

### ثالثًا: ارفع الفرع وافتح الطلب

```bash
git push origin fix/login-timeout
```

افتح بعد ذلك صفحة المستودع الأصلي، واختر «طلب دمج جديد»، ثم املأ القالب بالمعلومات الآتية:

- **العنوان:** جملة قصيرة تصف التغيير، على نمط رسالة الالتزام نفسه.
- **الوصف:** ما المشكلة؟ وكيف عالجتها؟ ولماذا اخترت هذا الحل دون غيره؟
- **المشكلة المرتبطة:** اكتب `Closes #123` لتُغلق المشكلة تلقائيًا عند الدمج.
- **طريقة التحقق:** الخطوات التي يتبعها المراجع ليتأكد بنفسه من صحة التغيير.
- **لقطات الشاشة:** إذا مسّ التغيير الواجهة.

### رابعًا: تعامل مع المراجعة

- يراجع طلبك مشرف واحد على الأقل قبل الدمج.
- أجب عن كل تعليق، إما بتعديل الشيفرة وإما بشرح سبب إبقائها كما هي.
- ارفع التعديلات في التزامات جديدة أثناء المراجعة ليسهل على المراجع تتبعها، وقد نطلب منك دمجها في التزام واحد قبل الدمج النهائي.
- إذا تقدّم الفرع الرئيسي وظهر تعارض في الدمج (Merge Conflict)، فأعد بناء فرعك عليه:

  ```bash
  git fetch upstream
  git rebase upstream/main
  git push --force-with-lease
  ```

- إذا وضعنا على طلبك وسم «يحتاج إلى معلومات» ولم يصلنا رد خلال 30 يومًا، فقد نغلقه، ويمكنك إعادة فتحه متى شئت.

## كتابة رسالة الالتزام

نتبع مواصفة الالتزامات التقليدية (Conventional Commits)، فهي تجعل السجل مقروءًا وتسمح بتوليد سجل التغييرات تلقائيًا.

### البنية

```text
<النوع>(<النطاق>): <ملخص قصير>

<المتن: ماذا تغيّر ولماذا>

<التذييل: مراجع المشكلات أو التغييرات الكاسرة>
```

### الأنواع المعتمدة

| النوع | الاستعمال |
|---|---|
| `feat` | ميزة جديدة |
| `fix` | إصلاح خطأ |
| `docs` | تغيير في التوثيق فقط |
| `test` | إضافة اختبارات أو تعديلها |
| `refactor` | إعادة هيكلة لا تغيّر السلوك |
| `perf` | تحسين الأداء |
| `chore` | مهام صيانة، مثل تحديث الاعتماديات |

### القواعد

- لا يتجاوز سطر الملخص 72 حرفًا.
- اكتب الملخص بصيغة الأمر، ولا تختمه بنقطة.
- اترك سطرًا فارغًا بين الملخص والمتن.
- اشرح في المتن **لماذا** أجريت التغيير، فالفرق في الشيفرة يوضّح **ماذا** تغيّر.
- إذا كسر التغيير التوافق مع الإصدارات السابقة، فاكتب في التذييل `BREAKING CHANGE:` متبوعًا بالشرح.

### مثال

```text
fix(auth): increase session timeout to 30 minutes

Users were being logged out while filling long forms because the
timeout was 5 minutes. The new value matches the API token lifetime.

Closes #123
```

## الاختبارات المطلوبة

لن ندمج أي طلب لا تجتاز فيه جميع الفحوص الآلية في خط التكامل المستمر (CI). شغّل الفحوص الآتية على جهازك قبل رفع الفرع لتوفّر وقتك ووقت المراجعين.

### الفحوص الإلزامية

1. **اختبارات الوحدة (Unit Tests):** أضف اختبارًا لكل دالة جديدة أو سلوك معدّل.
2. **اختبارات التكامل (Integration Tests):** مطلوبة إذا مسّ التغيير التفاعل بين الوحدات أو مع خدمات خارجية.
3. **فحص التنسيق والأسلوب:** يجب أن تخلو الشيفرة من تحذيرات أداة فحص الشيفرة (Linter).
4. **نسبة التغطية:** لا نقبل أي طلب يخفض نسبة تغطية الاختبارات (Test Coverage) عن 80%.

### تشغيل الفحوص محليًا

```bash
npm test            # اختبارات الوحدة
npm run test:int    # اختبارات التكامل
npm run lint        # فحص الأسلوب
npm run coverage    # تقرير التغطية
```

عدّل هذه الأوامر بما يناسب أدوات مشروعك.

### عند إصلاح خطأ

اكتب أولًا اختبارًا يفشل بسبب الخطأ، ثم أصلح الشيفرة حتى ينجح. يضمن ذلك ألا يعود الخطأ في المستقبل دون أن ننتبه له.

### ما الذي يجعل الاختبار جيدًا؟

- يختبر سلوكًا واحدًا، ويصف اسمه ذلك السلوك بوضوح.
- لا يعتمد على ترتيب تشغيل الاختبارات الأخرى ولا على الشبكة.
- يغطي الحالات الحدّية، مثل القيم الفارغة والمدخلات غير الصالحة.

## قائمة التحقق قبل الإرسال

- [ ] الفرع محدّث مع `upstream/main`.
- [ ] رسائل الالتزام تتبع المواصفة.
- [ ] جميع الاختبارات تنجح محليًا.
- [ ] أضفت اختبارات للتغييرات الجديدة.
- [ ] حدّثت التوثيق عند الحاجة.
- [ ] ربطت الطلب بالمشكلة المرتبطة به.

## هل تحتاج إلى مساعدة؟

إذا تعثّرت في أي خطوة، فاترك تعليقًا على طلبك أو على المشكلة، وسيساعدك أحد المشرفين. لا يوجد سؤال تافه، وكل مساهمة، مهما صغرت، محل تقدير.

---

هذا الدليل قالب عام، فاستبدل بالعناصر الآتية ما يناسب مشروعك قبل نشره: الأوامر (`npm`)، ونسبة التغطية (80%)، ومهلة الإغلاق (30 يومًا)، وروابط المستودع. وإذا أردت، أحفظه لك في ملف `CONTRIBUTING.md` داخل المستودع.
