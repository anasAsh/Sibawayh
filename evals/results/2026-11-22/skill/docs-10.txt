# دليل المساهمة

شكرًا لاهتمامك بالمساهمة في هذا المشروع! يشرح هذا الدليل كيف تفتح طلب دمج (Pull Request)، وكيف تكتب رسالة الالتزام (Commit Message)، وما الاختبارات التي يجب أن تنجح فيها مساهمتك قبل قبولها.

## قبل أن تبدأ

- ابحث في قائمة المشكلات (Issues) لتتأكد أن أحدًا لم يبلّغ عن المشكلة نفسها ولم يقترح الميزة نفسها.
- إذا كان التغيير كبيرًا، فافتح مشكلة أولًا وناقش الفكرة مع المشرفين قبل كتابة الشيفرة. هكذا توفّر وقتك ووقتهم.
- اقرأ مدونة السلوك (Code of Conduct) والتزم بها في كل نقاش.

## تجهيز بيئة العمل

1. أنشئ نسخة من المستودع في حسابك بالضغط على زر «Fork».
2. انسخ نسختك إلى جهازك:

   ```bash
   git clone https://github.com/<your-username>/<project>.git
   cd <project>
   git remote add upstream https://github.com/<org>/<project>.git
   ```

3. ثبّت الاعتماديات (Dependencies) باتباع التعليمات الواردة في ملف `README.md`.
4. أنشئ فرعًا جديدًا لكل تغيير، ولا تعمل على الفرع `main` مباشرة:

   ```bash
   git checkout -b fix/login-timeout
   ```

   اختر اسمًا قصيرًا يصف التغيير ويبدأ ببادئة مثل `feat/` للميزات أو `fix/` للإصلاحات أو `docs/` للتوثيق.

## كتابة رسالة الالتزام

نتبع مواصفة الالتزامات التقليدية (Conventional Commits)، لأنها تجعل السجل أسهل في القراءة وتتيح توليد ملاحظات الإصدار آليًا.

### البنية

```text
<type>(<scope>): <summary>

<body>

<footer>
```

- **النوع (`type`):** يحدد طبيعة التغيير، ويكون واحدًا مما يأتي:
  - للميزة الجديدة: `feat`
  - لإصلاح خطأ: `fix`
  - لتغيير التوثيق وحده: `docs`
  - لإعادة هيكلة لا تغيّر السلوك: `refactor`
  - لإضافة الاختبارات أو تعديلها: `test`
  - لمهام الصيانة مثل تحديث الاعتماديات: `chore`
- **النطاق (`scope`):** اختياري، ويحدد الجزء المتأثر من المشروع، مثل `auth` أو `api`.
- **الملخص (`summary`):** سطر واحد لا يتجاوز 72 حرفًا، بصيغة الأمر، وبلا نقطة في آخره.
- **المتن (`body`):** اختياري، ويشرح سبب التغيير وما الذي تغيّر، لا طريقة تنفيذه.
- **التذييل (`footer`):** يربط الالتزام بالمشكلة المعنية، أو ينبّه إلى تغيير يكسر التوافق.

### مثال

```text
fix(auth): handle expired session tokens gracefully

Users were logged out without warning when their token expired
mid-request. Refresh the token silently and retry once.

Closes #142
```

إذا كان تغييرك يكسر التوافق مع الإصدارات السابقة، فأضف علامة `!` بعد النوع، واشرح التغيير في التذييل بعد العبارة `BREAKING CHANGE:`.

### نصائح

- اجعل كل التزام وحدة منطقية واحدة. لا تخلط إصلاح خطأ بإعادة تنسيق ملفات لا علاقة لها به.
- اكتب رسائل الالتزام بالإنجليزية ليفهمها جميع المساهمين.
- راجع التزاماتك قبل دفعها، وادمج الالتزامات الصغيرة المتتالية عند الحاجة.

## الاختبارات المطلوبة

لن نقبل أي طلب لا تنجح فيه الاختبارات كلها. شغّل الفحوص الآتية على جهازك قبل فتح الطلب:

1. **اختبارات الوحدة (Unit Tests):** يجب أن تنجح جميعها:

   ```bash
   npm test
   ```

2. **فحص جودة الشيفرة (Linting):** يجب ألّا يظهر أي خطأ أو تحذير جديد:

   ```bash
   npm run lint
   ```

3. **تغطية الاختبارات (Test Coverage):** يجب ألّا تقل نسبة التغطية عن 80%، وأن تغطي اختباراتك الشيفرة الجديدة:

   ```bash
   npm run test:coverage
   ```

4. **اختبارات التكامل (Integration Tests):** شغّلها إذا كان تغييرك يمسّ واجهة برمجة التطبيقات (API) أو قاعدة البيانات:

   ```bash
   npm run test:integration
   ```

### ما الذي يجب اختباره؟

- **عند إصلاح خطأ:** أضف اختبارًا يفشل قبل الإصلاح وينجح بعده، حتى لا يعود الخطأ لاحقًا.
- **عند إضافة ميزة:** اختبر الحالة المعتادة والحالات الحدّية ومعالجة الأخطاء.
- **عند إعادة الهيكلة:** يجب أن تنجح الاختبارات الحالية دون تعديل. إذا اضطررت إلى تعديلها، فاشرح السبب في وصف الطلب.

يشغّل نظام التكامل المستمر (CI) هذه الفحوص كلها تلقائيًا على كل طلب دمج، وتظهر نتائجها في صفحة الطلب.

## فتح طلب الدمج

1. حدّث فرعك بآخر تغييرات المستودع الأصلي:

   ```bash
   git fetch upstream
   git rebase upstream/main
   ```

2. ادفع فرعك إلى نسختك:

   ```bash
   git push origin fix/login-timeout
   ```

3. افتح صفحة المستودع على منصة GitHub، واضغط «Compare & pull request».
4. اكتب عنوانًا واضحًا بصيغة رسالة الالتزام، مثل: `fix(auth): handle expired session tokens`.
5. املأ قالب الوصف، واذكر فيه:
   - **ماذا:** ملخص التغيير.
   - **لماذا:** المشكلة التي يحلها التغيير مع رابطها، مثل `Closes #142`.
   - **كيف اختبرته:** الخطوات التي اتبعتها للتحقق من صحة التغيير.
   - **لقطات الشاشة:** إذا كان التغيير يمسّ الواجهة.
6. فعّل خيار «Allow edits from maintainers» ليتمكن المشرفون من إجراء التعديلات الصغيرة مباشرة.

### قائمة التحقق قبل الإرسال

- [ ] يقتصر الطلب على تغيير واحد.
- [ ] تتبع رسائل الالتزام المواصفة المذكورة أعلاه.
- [ ] تنجح جميع الاختبارات وفحوص الجودة على جهازي.
- [ ] أضفت اختبارات للشيفرة الجديدة.
- [ ] حدّثت التوثيق عند الحاجة.

## المراجعة والدمج

- يراجع أحد المشرفين طلبك عادةً خلال 3 إلى 5 أيام عمل.
- ردّ على التعليقات بتعديل الشيفرة أو بالنقاش، وادفع تعديلاتك إلى الفرع نفسه، فيتحدّث الطلب تلقائيًا.
- لا نقبل الطلب إلا بعد موافقة مراجع واحد على الأقل ونجاح جميع فحوص التكامل المستمر.
- يدمج المشرفون الطلبات غالبًا بطريقة «Squash and merge»، فتصبح كل التزامات الطلب التزامًا واحدًا يحمل عنوان الطلب. لذلك احرص على أن يصلح العنوان رسالةَ التزام نهائية.

## هل تحتاج إلى مساعدة؟

إذا واجهتك أي صعوبة، فافتح مشكلة بالوسم `question` أو اسأل في قناة النقاش الخاصة بالمشروع. لا يوجد سؤال تافه، ونرحب دائمًا بالمساهمين الجدد.
