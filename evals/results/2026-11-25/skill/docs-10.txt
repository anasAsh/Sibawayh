# دليل المساهمة

شكرًا لاهتمامك بالمساهمة في المشروع. يشرح هذا الدليل كيف تجهّز تعديلك، وتكتب رسالة الالتزام (commit)، وتختبر ما كتبته، ثم تفتح طلب دمج (pull request) تسهل مراجعته.

## قبل أن تبدأ

- **ابحث أولًا:** راجع المشكلات (issues) وطلبات الدمج المفتوحة، فقد يكون غيرك يعمل على الفكرة نفسها.
- **ناقش التغييرات الكبيرة:** إن كنت تنوي إضافة ميزة أو تغيير سلوك قائم، فافتح مشكلة واشرح اقتراحك قبل كتابة الشيفرة. أما الأخطاء الإملائية والإصلاحات الصغيرة فأرسل طلب دمجها مباشرة.
- **أبلغ عن الثغرات الأمنية سرًّا:** راسل المشرفين بالطريقة المبيّنة في ملف `SECURITY.md`، ولا تنشر التفاصيل في مشكلة عامة.

## إعداد بيئة العمل

أنشئ تفريعًا (fork) للمستودع من صفحته، ثم انسخه إلى جهازك واربطه بالمستودع الأصلي:

```bash
git clone https://github.com/<username>/<project>.git
cd <project>
git remote add upstream https://github.com/<organization>/<project>.git
make setup
make test
```

إذا فشلت الاختبارات قبل أن تعدّل شيئًا، فأخبرنا في مشكلة جديدة واذكر نظام التشغيل ونص الخطأ.

بعد ذلك أنشئ فرعًا مستقلًّا لكل تعديل، ولا تعمل على الفرع `main` مباشرة:

```bash
git fetch upstream
git switch --no-track -c fix/empty-input upstream/main
```

ابدأ اسم الفرع بنوع التعديل، ثم أضف وصفًا قصيرًا له، مثل `feat/export-csv` أو `docs/install-guide`.

## كتابة رسالة الالتزام

اجعل كل التزام تغييرًا منطقيًّا واحدًا يمكن فهمه والتراجع عنه وحده. وتتبع رسائلنا مواصفة الالتزامات الاصطلاحية (Conventional Commits)، وبنيتها كما يلي:

```text
<type>(<scope>): <subject>

<body>

<footer>
```

### العنوان

يتكوّن العنوان من نوع التغيير، ثم نطاقه بين قوسين (اختياري)، ثم ملخص قصير. وهذه هي الأنواع المعتمدة:

| متى تستخدمه | النوع |
|---|---|
| إضافة ميزة جديدة | `feat` |
| إصلاح خطأ برمجي | `fix` |
| تعديل التوثيق وحده | `docs` |
| إعادة هيكلة لا تغيّر السلوك | `refactor` |
| تحسين الأداء | `perf` |
| إضافة اختبارات أو تصحيحها | `test` |
| تعديل ملفات التكامل المستمر (CI) | `ci` |
| صيانة لا تمسّ شيفرة المنتج، كتحديث الاعتماديات | `chore` |

والتزم في صياغته بما يلي:

- لا يتجاوز العنوان 72 حرفًا، ولا ينتهي بنقطة.
- يُكتب الملخص بالإنجليزية وبصيغة الأمر: `add` لا `added`.
- يصف الملخص التغيير نفسه، فلا تكتب عناوين مبهمة مثل `fix bug` أو `update code`.

### المتن والتذييل

اشرح في المتن **سبب** التغيير وأثره، فالشيفرة تبيّن ما تغيّر ولا تبيّن لماذا تغيّر. ويمكن الاستغناء عن المتن إن كان العنوان كافيًا. أما التذييل فاذكر فيه المشكلات المرتبطة، مثل `Closes #142`.

مثال على رسالة جيدة:

```text
fix(parser): skip blank lines in input files

The parser assumed that every line has at least one token, so it
crashed on files that contain blank lines.

Skip blank lines before tokenizing and add a regression test.

Closes #142
```

وإذا كان التغيير يكسر التوافق مع الإصدارات السابقة، فضع علامة `!` قبل النقطتين، واشرح في التذييل ما على المستخدم فعله:

```text
feat(api)!: return dates in ISO 8601 format

BREAKING CHANGE: the `created` field is now an ISO 8601 string instead
of a Unix timestamp. Update any client that reads it as a number.
```

## الاختبارات المطلوبة

لا ندمج تعديلًا يغيّر السلوك من دون اختبار يثبته. ويختلف المطلوب بحسب نوع التعديل:

| نوع التعديل | الاختبارات المطلوبة |
|---|---|
| إصلاح خطأ | اختبار انحدار (regression test) يفشل قبل الإصلاح وينجح بعده |
| ميزة جديدة | اختبارات وحدة للحالات المعتادة والحدّية وحالات الخطأ، واختبار تكامل إن تفاعلت الميزة مع مكوّنات أخرى |
| إعادة هيكلة | نجاح الاختبارات القائمة دون تعديل النتائج المتوقعة فيها؛ وأضف ما ينقص منها قبل أن تبدأ |
| تحسين أداء | نجاح الاختبارات القائمة، مع نتائج القياس قبل التعديل وبعده |
| تعديل التوثيق | لا اختبارات جديدة، لكن جرّب الأوامر والأمثلة التي عدّلتها |

### كيف تكتب اختبارًا جيدًا؟

- اختبر السلوك الظاهر لا تفاصيل التنفيذ الداخلية.
- اجعل كل اختبار مستقلًّا، لا يعتمد على غيره ولا على ترتيب التشغيل.
- تجنّب الاتصال الفعلي بالشبكة والاعتماد على الوقت الحالي، واستعمل بدائل وهمية (mocks) عند الحاجة.
- اختر اسمًا يصف الحالة المختبَرة، مثل `test_parser_skips_blank_lines`.

### تشغيل الفحوص محليًّا

شغّل هذه الأوامر قبل كل دفع إلى المستودع:

```bash
make lint
make test
make coverage
```

يجب ألا تقل تغطية الشيفرة التي أضفتها أو عدّلتها عن 80%. ولا تعطّل اختبارًا فاشلًا لكي ينجح البناء؛ فإن ظننت أن الاختبار نفسه خاطئ، فوضّح السبب في طلب الدمج.

## فتح طلب الدمج

1. حدّث فرعك وشغّل الفحوص قبل دفعه أول مرة:

   ```bash
   git fetch upstream
   git rebase upstream/main
   make lint && make test && make coverage
   git push -u origin fix/empty-input
   ```

2. افتح طلب دمج من فرعك إلى الفرع `main` في المستودع الأصلي. وإن لم يكتمل العمل وأردت رأيًا مبكرًا، فافتحه مسودةً (draft).
3. اكتب عنوان الطلب بصيغة عنوان الالتزام نفسها، لأننا ندمج التزامات الطلب في التزام واحد (squash merge) ونجعل عنوان الطلب عنوانًا له.
4. املأ الوصف بحسب القالب التالي:

```markdown
## ما الذي تغيّر؟

## لماذا نحتاج إلى هذا التغيير؟

Closes #

## كيف اختبرته؟

## ملاحظات للمراجعين

## قائمة التحقق

- [ ] راجعتُ التغييرات كاملةً بنفسي.
- [ ] أضفتُ الاختبارات المطلوبة أو حدّثتها.
- [ ] نجحت الفحوص والاختبارات على جهازي.
- [ ] حدّثتُ التوثيق إن تغيّر سلوك يراه المستخدم.
- [ ] وضّحتُ أي تغيير يكسر التوافق مع الإصدارات السابقة.
```

### نصائح لتسريع المراجعة

- اقتصر في الطلب على غرض واحد، وافصل إعادة الهيكلة عن تغيير السلوك.
- قسّم التعديل إن تجاوز نحو 400 سطر وأمكن تقسيمه.
- أرفق لقطتي شاشة، قبل التعديل وبعده، إن مسّ واجهة المستخدم.
- احذف كل تعديل لا صلة له بموضوع الطلب، كإعادة تنسيق ملفات أخرى.

## المراجعة والدمج

يُدمج الطلب إذا نجحت فحوص التكامل المستمر كلها، ووافق عليه مشرف واحد على الأقل، ولم تبقَ ملاحظات معلّقة.

- **الرد على الملاحظات:** عدّل الشيفرة أو اشرح سبب إبقائها كما هي. ونرحّب بالاختلاف في الرأي ما دام النقاش محترمًا ومتعلّقًا بالشيفرة.
- **إضافة التعديلات:** أضف التزامات جديدة، ولا تُعِد كتابة تاريخ الفرع بعد بدء المراجعة، كي يرى المراجعون ما استجدّ.
- **تأخر الرد:** إن مرّ أسبوع دون رد، فاكتب تعليقًا قصيرًا للتذكير. وقد نغلق الطلب إذا توقف العمل عليه 30 يومًا، فإن أردت استئنافه فاطلب إعادة فتحه.
- **حل التعارضات:** ادمج الفرع `main` من المستودع الأصلي في فرعك، وحُلّ ما يظهر من تعارضات، ثم أعد تشغيل الاختبارات قبل الدفع:

```bash
git fetch upstream
git merge upstream/main
make test
git push
```

وإن تعذّرت عليك خطوة من هذه الخطوات، فاسأل في المشكلة المرتبطة أو في طلب الدمج نفسه.
