# خطة نقل قاعدة البيانات من MySQL إلى PostgreSQL

## المرحلة الأولى: التقييم والتحضير (2–3 أسابيع)

- **جرد قاعدة البيانات:** حصر الجداول، الفهارس، الإجراءات المخزنة، المشغّلات (Triggers)، والعروض (Views)، مع أحجام البيانات.
- **تحليل التوافق:** تحديد الفروقات بين النظامين، وأهمها:
  - أنواع البيانات (`TINYINT(1)` ← `BOOLEAN`، `DATETIME` ← `TIMESTAMP`، `AUTO_INCREMENT` ← `IDENTITY`، `ENUM`).
  - صياغة SQL الخاصة بـ MySQL في كود التطبيق (علامات الاقتباس العكسية، `LIMIT x,y`، `ON DUPLICATE KEY UPDATE`، `GROUP BY` المتساهل).
  - حساسية حالة الأحرف في المقارنات النصية والترتيب (Collation).
- **اختيار الأدوات:** مثل `pgloader` للنقل المباشر، أو AWS DMS / Debezium للنقل مع التزامن المستمر.
- **تجهيز بيئة PostgreSQL** تجريبية مطابقة لبيئة الإنتاج، وتحديد معايير النجاح وخطة التراجع.

**المخرجات:** تقرير توافق، قائمة بالتعديلات المطلوبة في الكود، وجدول زمني معتمد.

## المرحلة الثانية: التحويل والاختبار (4–6 أسابيع)

- **تحويل المخطط (Schema):** إنشاء الجداول والفهارس والقيود في PostgreSQL، وإعادة كتابة الإجراءات المخزنة والمشغّلات بلغة PL/pgSQL.
- **تعديل التطبيق:** تحديث الاستعلامات غير المتوافقة وإعدادات الاتصال وطبقة ORM.
- **نقل تجريبي كامل للبيانات** على نسخة من بيانات الإنتاج، وقياس المدة الفعلية.
- **التحقق من سلامة البيانات:** مقارنة أعداد الصفوف، المجاميع الاختبارية (Checksums)، وعينات من السجلات.
- **اختبارات الأداء والوظائف:** تشغيل مجموعة الاختبارات كاملة، واختبار الحمل، وضبط الفهارس وإعدادات PostgreSQL.
- **تجربة خطة التراجع** فعليًا، لا نظريًا فقط.

**المخرجات:** مخطط محوَّل، تطبيق متوافق، نتائج اختبار موثقة، ومدة نقل معروفة.

## المرحلة الثالثة: الانتقال والتشغيل (1–2 أسبوع)

- **تفعيل التزامن المستمر** (CDC) بين MySQL و PostgreSQL لتقليل زمن التوقف.
- **نافذة الانتقال:** إيقاف الكتابة على MySQL، انتظار اكتمال التزامن، التحقق النهائي من البيانات، ثم تحويل التطبيق إلى PostgreSQL.
- **مراقبة مكثفة** بعد الانتقال: الاستعلامات البطيئة، الأخطاء، استهلاك الموارد.
- **الإبقاء على MySQL** في وضع القراءة فقط لمدة 2–4 أسابيع كخيار للتراجع، ثم إيقافه نهائيًا.

**المخرجات:** نظام إنتاجي يعمل على PostgreSQL، وتوثيق محدَّث.

## المخاطر المتوقعة

| الخطر | الأثر | المعالجة |
|---|---|---|
| فقدان أو تلف بيانات أثناء التحويل (ترميز النصوص، التواريخ الصفرية `0000-00-00`، اقتطاع القيم) | مرتفع | تحقق آلي بالمجاميع الاختبارية، ونقل تجريبي متكرر قبل الإنتاج |
| اختلاف سلوك الاستعلامات (حساسية الأحرف، الترتيب، التعامل مع `NULL`) | مرتفع | اختبارات وظيفية شاملة، ومقارنة نتائج الاستعلامات الحرجة بين النظامين |
| تراجع الأداء لاستعلامات معينة | متوسط | اختبار حمل مبكر، تحليل `EXPLAIN`، وضبط الفهارس والإعدادات |
| تجاوز زمن التوقف للنافذة المحددة | متوسط | استخدام CDC، وقياس المدة في التجارب، وتحديد نقطة قرار واضحة للتراجع |
| صعوبة تحويل الإجراءات المخزنة والمشغّلات | متوسط | حصرها مبكرًا في المرحلة الأولى، وإعادة كتابتها يدويًا مع اختبارات لكل منها |
| فشل التراجع بعد بدء الكتابة على PostgreSQL | مرتفع | تزامن عكسي نحو MySQL خلال الفترة الأولى، أو تحديد مهلة قصيرة لقرار التراجع |
| نقص خبرة الفريق في PostgreSQL | متوسط | تدريب مسبق، وإعداد أدلة تشغيل للنسخ الاحتياطي والمراقبة والصيانة (`VACUUM`) |
| أنظمة تابعة غير محصورة (تقارير، مهام مجدولة، تكاملات خارجية) | متوسط | مراجعة سجلات الاتصال بـ MySQL لحصر كل العملاء قبل الانتقال |

المدد المذكورة تقديرية لقاعدة بيانات متوسطة الحجم، وتتغير بحسب حجم البيانات وعدد الإجراءات المخزنة ومدى اعتماد التطبيق على خصائص MySQL.
