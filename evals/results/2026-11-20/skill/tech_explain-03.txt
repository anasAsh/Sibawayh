## كيف يعمل `git rebase`

يأخذ الأمر `git rebase` الإيداعات (commits) التي أنشأتها على فرعك، ثم يعيد تطبيقها واحدًا تلو الآخر فوق قاعدة جديدة، وهذه القاعدة عادةً آخر نسخة من `main`. والنتيجة تاريخ خطي، كأنك بدأت العمل من آخر نقطة في `main`.

قبل:

```
      A---B---C  feature
     /
D---E---F---G  main
```

بعد تنفيذ `git rebase main` وأنت على الفرع `feature`:

```
              A'--B'--C'  feature
             /
D---E---F---G  main
```

لاحظ أن `A'` و`B'` و`C'` إيداعات جديدة لها معرّفات (hashes) مختلفة، لأن Git ينسخ الإيداعات ولا ينقلها.

أما `git merge main` فيترك الإيداعات كما هي، ويضيف إيداع دمج (merge commit) يجمع الفرعين. بهذا يحفظ التاريخ كما حدث فعلًا، لكن التاريخ يصبح متشعبًا.

## متى تفضّل `rebase`

- لتحديث فرعك المحلي بآخر تغييرات `main` قبل فتح طلب الدمج (Pull Request).
- لتنظيف إيداعاتك قبل مشاركتها، كضمّ الإيداعات الصغيرة أو تعديل رسائلها عبر `git rebase -i`.
- حين يفضّل الفريق تاريخًا خطيًا يسهل قراءته وتتبعه بأدوات مثل `git bisect`.

## متى تفضّل `merge`

- إذا كان الفرع مشتركًا ودفعه آخرون إلى المستودع البعيد.
- عند دمج فرع مكتمل في `main` مع الاحتفاظ بأثر واضح لعملية الدمج.
- إذا أردت تاريخًا يعكس ما حدث فعلًا دون إعادة كتابة.

**القاعدة الذهبية:** لا تُعِد كتابة تاريخ فرع دفعته ويعمل عليه غيرك، لأن `rebase` يغيّر معرّفات الإيداعات فيُربك زملاءك.

## مثال عملي

```bash
git switch feature
git fetch origin
git rebase origin/main

# عند حدوث تعارض: أصلح الملفات ثم
git add <file>
git rebase --continue
# أو تراجع عن العملية كلها
git rebase --abort

# بعد إعادة الكتابة يلزم الدفع القسري الآمن
git push --force-with-lease

# ثم دمج سريع في main دون إيداع دمج
git switch main
git merge --ff-only feature
```
