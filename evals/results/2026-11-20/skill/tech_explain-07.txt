## ما واجهة REST API؟

**واجهة برمجة التطبيقات (API)** مجموعة من القواعد تسمح لبرنامجين بالتواصل وتبادل البيانات. أما **REST** (اختصار Representational State Transfer، أي «نقل الحالة التمثيلية») فأسلوب معماري لتصميم هذه الواجهات عبر بروتوكول HTTP، وضعه روي فيلدنغ (Roy Fielding) عام 2000.

تقوم فكرة REST على أن كل شيء في النظام **مورد (Resource)**: مستخدم أو منتج أو طلب مثلًا. ولكل مورد عنوان فريد (URL)، ويتعامل العميل معه بطرق HTTP القياسية.

### أهم مبادئ REST

- **الفصل بين العميل والخادم:** يتولى العميل الواجهة، ويتولى الخادم البيانات ومنطق العمل، فيتطور كل منهما مستقلًا عن الآخر.
- **انعدام الحالة (Stateless):** يحمل كل طلب كل ما يحتاج إليه الخادم لفهمه، ولا يحفظ الخادم شيئًا عن الطلبات السابقة.
- **قابلية التخزين المؤقت (Cacheable):** تبيّن الاستجابة هل يجوز تخزينها مؤقتًا لتسريع الطلبات اللاحقة.
- **واجهة موحدة:** يُتعامل مع كل الموارد بالأسلوب نفسه، أي بعناوين واضحة وطرق HTTP ثابتة.
- **تمثيل البيانات:** تُرسَل البيانات غالبًا بصيغة JSON، وقد تُرسَل بصيغ أخرى مثل XML.

## أشهر طرق HTTP

تستخدم الأمثلة التالية واجهة افتراضية لإدارة المستخدمين عنوانها الأساسي `https://api.example.com`.

### طريقة GET: جلب البيانات

تقرأ هذه الطريقة موردًا أو قائمة موارد دون أن تغيّر شيئًا على الخادم، لذلك تُعدّ **آمنة** و**متساوية الأثر (Idempotent)**، أي أن تكرار الطلب نفسه لا يغيّر حالة الخادم.

```http
GET /users/42 HTTP/1.1
Host: api.example.com
```

الاستجابة:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "id": 42, "name": "سارة", "email": "sara@example.com" }
```

### طريقة POST: إنشاء مورد جديد

ترسل هذه الطريقة بيانات إلى الخادم لينشئ بها موردًا جديدًا. وهي **ليست متساوية الأثر**: إذا أرسلت الطلب مرتين فقد يُنشأ مستخدمان.

```http
POST /users HTTP/1.1
Host: api.example.com
Content-Type: application/json

{ "name": "أحمد", "email": "ahmad@example.com" }
```

الاستجابة:

```http
HTTP/1.1 201 Created
Location: /users/43

{ "id": 43, "name": "أحمد", "email": "ahmad@example.com" }
```

### طريقة PUT: تحديث مورد أو استبداله

تستبدل هذه الطريقة المورد كاملًا بالبيانات المرسلة، فإذا أغفلت حقلًا فقد يُحذف أو يعود إلى قيمته الافتراضية. وهي **متساوية الأثر**، لأن إرسال الطلب نفسه مرات عدة يترك المورد في الحالة نفسها.

```http
PUT /users/43 HTTP/1.1
Host: api.example.com
Content-Type: application/json

{ "name": "أحمد علي", "email": "ahmad.ali@example.com" }
```

الاستجابة:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "id": 43, "name": "أحمد علي", "email": "ahmad.ali@example.com" }
```

إذا أردت تعديل حقل واحد فقط فاستخدم `PATCH`، وهي طريقة تطبّق تعديلًا جزئيًّا على المورد.

### طريقة DELETE: حذف مورد

تحذف هذه الطريقة المورد المحدد في العنوان. وهي **متساوية الأثر** أيضًا: بعد الحذف الأول يبقى المورد محذوفًا مهما كررت الطلب.

```http
DELETE /users/43 HTTP/1.1
Host: api.example.com
```

الاستجابة:

```http
HTTP/1.1 204 No Content
```

## ملخص

| الطريقة | الوظيفة | مثال | آمنة | متساوية الأثر |
|---|---|---|---|---|
| `GET` | قراءة | `GET /users/42` | نعم | نعم |
| `POST` | إنشاء | `POST /users` | لا | لا |
| `PUT` | استبدال أو تحديث كامل | `PUT /users/43` | لا | نعم |
| `PATCH` | تحديث جزئي | `PATCH /users/43` | لا | ليس بالضرورة |
| `DELETE` | حذف | `DELETE /users/43` | لا | نعم |

### رموز الحالة الشائعة

- **رمز 200 (OK):** نجح الطلب.
- **رمز 201 (Created):** أُنشئ مورد جديد.
- **رمز 204 (No Content):** نجح الطلب ولا محتوى في الاستجابة.
- **رمز 400 (Bad Request):** الطلب غير صالح.
- **رمز 401 (Unauthorized):** يلزم التحقق من الهوية.
- **رمز 404 (Not Found):** المورد غير موجود.
- **رمز 500 (Internal Server Error):** حدث خطأ في الخادم.

باختصار: تنظّم REST الواجهة حول **موارد** لكل منها عنوان، وتحدد طريقة HTTP **الإجراء** المطلوب على المورد: GET للقراءة، وPOST للإنشاء، وPUT للتحديث، وDELETE للحذف.
