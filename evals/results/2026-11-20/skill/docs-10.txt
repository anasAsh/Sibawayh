# دليل المساهمة

شكرًا لاهتمامك بالمساهمة في هذا المشروع! يشرح هذا الدليل الخطوات التي نتبعها لقبول المساهمات، من تجهيز بيئة العمل إلى دمج التعديلات في الفرع الرئيسي. اقرأه كاملًا قبل أن تفتح أول طلب دمج (pull request)، فهو يوفّر عليك وعلى المراجعين وقتًا كثيرًا.

## قبل أن تبدأ

- **ابحث في المشكلات المفتوحة (issues):** ربما أبلغ أحد قبلك عن الخطأ نفسه أو اقترح الميزة نفسها.
- **ناقش التغييرات الكبيرة أولًا:** إذا كنت تنوي إضافة ميزة جديدة أو تعديل بنية المشروع، فافتح مشكلة تشرح فيها الفكرة. انتظر موافقة أحد المشرفين قبل أن تكتب الشيفرة.
- **اطّلع على قواعد السلوك:** نتوقع من جميع المساهمين احترام مدونة قواعد السلوك المرفقة بالمستودع.

## تجهيز بيئة العمل

أنشئ نسخة مشتقة (fork) من المستودع في حسابك، ثم انسخها إلى جهازك. بعد ذلك أضف المستودع الأصلي مصدرًا بعيدًا باسم `upstream`:

```bash
git clone https://github.com/<اسم-المستخدم>/<المشروع>.git
cd <المشروع>
git remote add upstream https://github.com/<المنظمة>/<المشروع>.git
```

ثبّت الاعتماديات وتأكد من نجاح الاختبارات قبل أي تعديل. بهذا تعرف أن أي فشل لاحق سببه تغييراتك:

```bash
make install
make test
```

## فتح طلب دمج

### الخطوة الأولى: أنشئ فرعًا جديدًا

لا تعمل على الفرع `main` مباشرة. حدّث نسختك من المستودع الأصلي، ثم أنشئ فرعًا يدل اسمه على محتواه:

```bash
git fetch upstream
git switch -c fix/login-timeout upstream/main
```

نستخدم البادئات التالية لأسماء الفروع:

| البادئة | الاستخدام |
|---|---|
| `feat/` | ميزة جديدة |
| `fix/` | إصلاح خطأ |
| `docs/` | تعديل التوثيق |
| `refactor/` | إعادة هيكلة الشيفرة دون تغيير سلوكها |
| `test/` | إضافة اختبارات أو تحسينها |

### الخطوة الثانية: اجعل التغيير صغيرًا ومركّزًا

يعالج كل طلب دمج مسألة واحدة فقط. إذا وجدت أثناء عملك خطأً آخر لا علاقة له بمهمتك، فافتح له مشكلة أو طلب دمج مستقلًا. تُراجَع الطلبات الصغيرة أسرع، ويسهل التراجع عنها إذا ظهرت مشكلة.

### الخطوة الثالثة: ارفع الفرع وافتح الطلب

```bash
git push origin fix/login-timeout
```

افتح بعد ذلك طلب الدمج من صفحة المستودع على GitHub، واملأ القالب بالمعلومات التالية:

- **العنوان:** جملة قصيرة تصف التغيير، وتتبع صيغة رسائل الإيداع الموضحة أدناه.
- **الوصف:** ما المشكلة؟ وكيف حللتها؟ ولماذا اخترت هذا الحل دون غيره؟
- **المشكلة المرتبطة:** اكتب `Closes #123` ليُغلق الطلب المشكلة تلقائيًا عند دمجه.
- **طريقة التحقق:** الخطوات التي يتبعها المراجع ليتأكد بنفسه من صحة التغيير.
- **لقطات الشاشة:** أرفقها إذا غيّرت شيئًا في الواجهة.

إذا لم يكتمل عملك بعد وأردت رأيًا مبكرًا، فافتح الطلب **مسودةً** (Draft).

### الخطوة الرابعة: تعامل مع المراجعة

- ردّ على كل تعليق، حتى لو اكتفيت بكلمة «تم» بعد تطبيقه.
- أضف إيداعات جديدة لمعالجة الملاحظات بدلًا من إعادة كتابة السجل أثناء المراجعة، فهذا يسهّل على المراجع رؤية ما تغيّر.
- إذا تأخر الفرع عن `main` أو ظهر تعارض دمج، فأعد تأسيسه على أحدث نسخة:

```bash
git fetch upstream
git rebase upstream/main
git push --force-with-lease
```

لا يُدمج الطلب إلا بعد موافقة مراجع واحد على الأقل ونجاح جميع فحوص التكامل المستمر (CI).

## كتابة رسالة الإيداع

نتبع مواصفة [الإيداعات التقليدية (Conventional Commits)](https://www.conventionalcommits.org/). تتكوّن الرسالة من ثلاثة أجزاء:

```text
<النوع>(<النطاق>): <ملخص قصير>

<المتن: يشرح ماذا تغيّر ولماذا>

<التذييل: مراجع المشكلات أو التغييرات الجذرية>
```

### الأنواع المعتمدة

| النوع | متى تستخدمه |
|---|---|
| `feat` | إضافة ميزة جديدة |
| `fix` | إصلاح خطأ |
| `docs` | تعديل التوثيق فقط |
| `style` | تنسيق لا يغيّر منطق الشيفرة |
| `refactor` | إعادة هيكلة دون إضافة ميزة أو إصلاح خطأ |
| `perf` | تحسين الأداء |
| `test` | إضافة اختبارات أو تصحيحها |
| `chore` | مهام الصيانة وأدوات البناء |

### قواعد الكتابة

- اكتب سطر الملخص بصيغة الأمر: `add` لا `added`، و`fix` لا `fixes`.
- لا تتجاوز 72 حرفًا في سطر الملخص، ولا تنهه بنقطة.
- اترك سطرًا فارغًا بين الملخص والمتن.
- اشرح في المتن **لماذا** أجريت التغيير، أما **كيف** فتوضحه الشيفرة نفسها.
- إذا كسر التغيير التوافق مع الإصدارات السابقة، فأضف علامة `!` بعد النوع، واكتب في التذييل `BREAKING CHANGE:` ثم الشرح.

### أمثلة

رسالة جيدة:

```text
fix(auth): extend session timeout to 30 minutes

Users on slow connections were logged out before the login
request completed. The previous 5-second limit was too short
for the token refresh round trip.

Closes #482
```

رسائل ينبغي تجنبها:

```text
fixed stuff
WIP
update auth.py
```

## الاختبارات المطلوبة

لن يُدمج أي طلب لا يجتاز جميع الاختبارات. ونطلب أيضًا ما يلي:

### اختبارات للشيفرة الجديدة

- **كل ميزة جديدة** تحتاج إلى اختبارات وحدة (unit tests) تغطي الحالات العادية والحالات الحدّية وحالات الخطأ.
- **كل إصلاح لخطأ** يحتاج إلى اختبار يفشل قبل الإصلاح وينجح بعده، حتى لا يعود الخطأ مستقبلًا.
- **التغييرات التي تمس أكثر من وحدة** تحتاج إلى اختبارات تكامل تتحقق من أن المكونات تعمل معًا.

### الفحوص التي يجب أن تنجح على جهازك

شغّل الأوامر التالية قبل رفع الفرع:

```bash
make lint        # أداة فحص الشيفرة والتنسيق
make typecheck   # التحقق من الأنواع
make test        # جميع الاختبارات
make coverage    # تقرير التغطية
```

### نسبة التغطية

يجب ألا تقل تغطية الشيفرة الجديدة عن 80%، وألا يخفض طلبك التغطية الكلية للمشروع. يعرض خط التكامل المستمر تقرير التغطية تلقائيًا في صفحة الطلب.

### إرشادات كتابة الاختبارات

- سمِّ الاختبار باسم يصف السلوك المتوقع، مثل `test_returns_error_when_token_expired`.
- اجعل كل اختبار مستقلًا عن غيره، فلا يعتمد على ترتيب التنفيذ أو على حالة يتركها اختبار آخر.
- استخدم بيانات وهمية بدلًا من الاتصال بخدمات خارجية حقيقية.
- لا تترك اختبارًا متجاوَزًا (`skip`) دون سبب موثّق. إن لم يكن له سبب، فاحذفه.

## قائمة التحقق قبل الإرسال

- [ ] الفرع محدَّث مع `main` ولا توجد تعارضات.
- [ ] رسائل الإيداع تتبع الصيغة المعتمدة.
- [ ] أضفت اختبارات للشيفرة الجديدة أو للخطأ الذي أصلحته.
- [ ] تنجح جميع الفحوص على جهازك.
- [ ] حدّثت التوثيق إذا غيّرت سلوكًا يراه المستخدم.
- [ ] ربطت الطلب بالمشكلة المرتبطة به.

## هل تحتاج إلى مساعدة؟

إذا واجهتك صعوبة في أي خطوة، فاسأل في قسم النقاشات بالمستودع أو اترك تعليقًا في طلبك. لا يوجد سؤال بسيط، ويسعدنا أن نساعد المساهمين الجدد.

---

**قبل النشر:** الأوامر `make install` و`make lint` و`make typecheck` و`make coverage`، ونسبة التغطية 80%، أمثلة افتراضية. استبدلها بأدوات مشروعك الفعلية وقيمه. يمكنني أيضًا حفظ الدليل في المستودع باسم `CONTRIBUTING.md` إن أردت.
